# 07 — UI

## 1. Pieces

| Technology | Role |
|---|---|
| React Flow | canvas, node/edge rendering, zoom/pan, selection, drag, minimap, controls |
| ELK.js | **hierarchical** auto layout (ELK supports nested graphs natively — required for loop/try/parallel subgraphs): leaf nodes are measured first (render-measure by content/mode), then ELK computes child positions relative to the parent and the parent's size from its children; it understands no semantics; runs async |
| Monaco | code view, custom-code editor, diff view, developer mode |
| shadcn/ui | inspector forms, palette, dialogs |

Layout never changes the semantic graph.

## 4. Progressive disclosure

| Level | What you see |
|---|---|
| **Beginner** | a chain of labelled nodes with icons: `Get PRs → Check Auth → Send Slack`; edited through simple forms |
| **Power user** | the full inspector: fields, `{{ }}` expressions, conditions, loop config |
| **Developer** | Monaco with the full source, the custom-code editor, the diff view |

One graph, three levels of view — not three representations.

## 5. Editing UX

The user can ([06-patch-engine.md](06-patch-engine.md) §2): edit editable fields, expressions, conditions and loop config; add a node from the palette (a tool or a library function — the patcher inserts the import when needed); delete a node; change to a compatible tool; open custom code in Monaco.

For the function library ([05-registry.md](05-registry.md) §4) the UI adds:

- **create a new function**: open Monaco, write the function and declare its input/output, save it to the library → it appears in the palette immediately;
- **promote**: right-click a local function / custom code node → "Save to library";
- **edit a library function**: from any node using it → "Edit Code" → change the source; if the signature changes, the open flow shows diagnostics immediately and other flows show them when they are reloaded (the realistic scope — [05-registry.md](05-registry.md) §4).

Mandatory UX rules:

- an unsupported operation → the UI says so immediately ("Moving a node between branches is not supported yet — use the code view"), it never fails silently and never does something approximately right;
- `code`/`unknown` nodes are visually distinct (their own border/style) so the user knows that region can only be edited as code;
- diagnostics appear on the node they belong to (a badge) plus in an overall panel;
- every edit can optionally be previewed as a diff before it is applied.

## 6. End-to-end example

The code (the canonical example of these specs — [01-flow-contract.md](01-flow-contract.md) §1):

```ts
import type { Tools } from "../generated/tools";
import { isAuthChange } from "@flows/lib";

export default async function flow(input: { repository: string }, tools: Tools) {
  const prs = await tools.github.getNewPRs({ repo: input.repository });
  for (const pr of prs) {
    const files = await tools.github.getFiles({ pr });
    if (files.some(isAuthChange)) {
      await tools.slack.send({
        channel: "#security",
        message: `Security PR: ${pr.title}`
      });
    }
  }
}
```

The projection — **this is the canonical expected graph** that the acceptance test ([08-mvp.md](08-mvp.md) §4) checks against. The full node list: `trigger`, `tool`(getNewPRs), `loop`, `tool`(getFiles), `condition`, `tool`(slack.send), `output`(synthetic — the flow has no explicit return):

```text
┌─────────────┐
│ ⚡ Trigger   │
└──────┬──────┘
       │ data: input.repository ─────→ Get New PRs
       ▼
┌─────────────┐
│ Get New PRs │
└──────┬──────┘
       │ data: prs
       ▼
┌───────────────────────────────────────────┐
│ For Each pr in prs                        │
│   (data: pr → Get PR Files, Slack Send)   │
│  ┌──────────────┐                         │
│  │ Get PR Files │                         │
│  └──────┬───────┘                         │
│         │ data: files                     │
│         ▼                                 │
│  ┌─────────────────────┐                  │
│  │ ◇ Is Auth Change?   │  ← condition node,
│  └──────┬───────┬──────┘    label from the registry (04 §2.2b),
│    true │       │ false     expression: files.some(isAuthChange)
│         ▼       │                         │
│  ┌────────────┐ │                         │
│  │ 💬 Slack   │ │                         │
│  │  #security │ │                         │
│  └──────┬─────┘ │                         │
│         └───────┴──→ (end of the iteration│
│                       — NO merge node:    │
│                       the branches end the│
│                       block, 04 §2.4)     │
└──────────────────┬────────────────────────┘
                   ▼
            ┌─────────────┐
            │ ⏹ Output    │  synthetic — 04 §2.10
            └─────────────┘
```

Details to check against: `isAuthChange` is not a node of its own (it is a callback inside the condition expression — 04 §2.2b); there is no merge node inside the loop because both branches of the condition end the block (04 §2.4); the data edges are `input.repository` (trigger→getNewPRs), `prs` (getNewPRs→loop), `pr` (loop→getFiles and loop→slack.send, because of `pr.title` in the message), and `files` (getFiles→condition).

The user changes the channel `#security` → `#security-team` in the inspector → exactly one line is patched ([06-patch-engine.md](06-patch-engine.md) §4) → the graph re-renders and everything else stays as it was.

## 7. Performance targets

For a typical flow file (a few hundred lines):

- initial analysis: **< 500 ms** — reachable because building the graph needs only **parse + scope analysis** (tool resolution is binding-rooted, [04-analyzer.md](04-analyzer.md) §1.2) and **no** full type check;
- analysis after an edit: **< 100 ms** — warm reuse: keep the parse tree/Project alive, re-parse the file, re-analyze;
- **type-check enrichment** (types for ports, validation) is a separate layer running async in Node/CI or in a web worker — it arrives afterwards and never blocks building and showing the graph; where the browser cannot type-check, the graph is still complete, it just lacks detailed types on the ports;
- incremental UI updates through `GraphChange[]` — "an unchanged node does not re-render" applies to **React component rendering** (memoized on node data); **positions** are different: one structural change can make ELK move many nodes, which is accepted, because moving a node does not re-render its contents;
- layout runs async and never blocks interaction.

These are engineering targets, not semantic guarantees.
