# 09 — Future

## 1. Relationship to the sandbox runtime

CodeFlow's output is source + graph. Execution is handed to another system:

```text
CodeFlow (convert + edit)
   │
   ├── V8 isolate + bindings (the Cloudflare Code Mode model)
   ├── Temporal / Inngest / Trigger.dev / BullMQ
   └── Custom runtime
```

The seam is already prepared in the MVP: the `Tools` interface generated by the registry ([05-registry.md](05-registry.md) §2) *is* the binding contract — a runtime only has to inject a `tools` object satisfying that interface into the sandbox (an isolate with no general network access, API keys hidden behind the binding). Building the runtime requires no change to the core model.

A runtime unlocks graph-aware features:

- **execution tracing / visual debugging** — the runtime reports which statement is running → CodeFlow maps it back through source mapping → highlight the running node, show data flowing along the edges;
- **step-through / replay** on the graph;
- **run history** per node.

This is why precise source mapping matters from the MVP onwards: it does not only serve editing, it serves observability later.

## 2. Extending the analyzer (deliberately, one step at a time)

(`try/catch`, early `return`/`continue`/`break`, and bounded `while` have already moved into MVP scope, [04-analyzer.md](04-analyzer.md) §2.7–2.9.)

In order of value/difficulty:

1. smart projection — merge `filter().map().sort()` into one "Transform" node (deferred from v0.1: it needs a mapping mechanism for multi-statement regions and editable fields for merged nodes);
2. error handling as a port — project a `try/catch` wrapping a single tool call into an "error output port" on the tool node itself (n8n style) instead of a try node around it — sugar on top of the MVP's 1:1 try node;
3. `Promise.allSettled` / race; `switch`;
4. multi-file flows — importing helpers/subflows from other files;
5. JavaScript (no types → tool resolution by heuristic + registry name).

Every construct added must come with: an analyzer rule + a patcher rule + identity tests + round-trip tests. No construct is added "just to display it".

## 3. Structural editing

The hardest part, to be done once the MVP loop has real users:

- moving a node into/out of an `if` / `for`;
- reordering nodes (with a data-dependency check);
- wrapping a selection into a condition/loop;
- extracting a selection into a named function (custom code node).

## 4. Workflow-first creation

The MVP is code-first (the AI writes the code first). Later we can support the other direction — "the user drags nodes to build a new flow on a blank canvas" — which in essence means **generating contract-conforming flow code from the manipulated graph** and immediately returning to the standard model (code is truth). It must never become a parallel "graph is truth" mode.

## 5. AI in the loop

- AI-assisted node editing — the user describes a change to a node in natural language and the AI produces a patch (through the real patch engine, never a regeneration);
- AI generating a flow from an intent + registry context (the typed Tools API in the prompt);
- semantic diff/review — "what changed in this flow since yesterday" shown as a graph diff instead of a text diff.

## 6. Other

- reusable subflows / nested workflows;
- Git-aware source mapping (identity across commits);
- visual diff between workflow versions;
- collaborative editing (several users viewing/editing at once — requires lifting the single-editor assumption of conflict detection);
- more languages (Python is the first candidate — it has the same "AI writes it well" standing).

## 7. Permanent architectural constraint

Repeated here to prevent drift: CodeFlow **never** becomes a second workflow language.

```text
❌ Workflow JSON → Custom Runtime → Generated Code
✅ TypeScript Code → Semantic Graph → Visual Projection
```

The graph exists to understand and edit code, not to replace it.
