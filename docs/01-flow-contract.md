# 01 — Flow Code Contract

**The most important design decision in v0.2.** CodeFlow's input is not "any TypeScript" but **flow code that follows a contract**. That turns the analyzer from a research problem (reverse-engineering arbitrary code) into an engineering problem (analyzing code whose shape is known in advance).

Because the code is generated by an AI whose prompt we control, this contract is not a restriction on the user — it is an agreement between CodeFlow and the AI. Code that departs from the contract still works (it falls through to custom code nodes), but code that follows it maps to the largest number of meaningful nodes.

## 1. Flow unit

**1 flow = 1 TypeScript file, exporting a single default async function.**

```ts
import type { Tools } from "../generated/tools";
import { isAuthChange } from "@flows/lib";   // library function — 05-registry.md §4

export default async function flow(
  input: { repository: string },
  tools: Tools
) {
  const prs = await tools.github.getNewPRs({ repo: input.repository });

  for (const pr of prs) {
    const files = await tools.github.getFiles({ pr });

    if (files.some(isAuthChange)) {
      await tools.slack.send({
        channel: "#security",
        message: `Security PR: ${pr.title}`
      });
    }
  }
}
```

> This is the **canonical example** used throughout the specs (analyzer [04](04-analyzer.md), UI [07](07-ui.md) §6, acceptance [08](08-mvp.md) §4) — its expected graph is defined in exactly one place: [07-ui.md](07-ui.md) §6.

The contract solves several problems at once:

| Element | Role |
|---|---|
| `input` (parameter 1) | The trigger payload. The **trigger node** in the UI is built from this parameter's type plus external metadata (webhook/cron/manual, configured by the runtime) — not guessed from the code. |
| `tools` (parameter 2) | The single access point to tools/MCP. A typed interface generated by the registry ([05-registry.md](05-registry.md)). The analyzer resolves tool calls through the **symbol** of this interface, not by string matching. It is also exactly the bindings object the sandbox runtime injects at execution time — the two layers line up naturally. |
| Library/local functions | Custom logic (the escape hatch). Called as a statement → `function` node; used as a callback inside an expression → not a node of its own (see [04-analyzer.md](04-analyzer.md) §2.2b). |
| Return value | The flow's result, shown on the final node (output). |

## 1b. The callable sources inside a flow

A step in a flow can call one of four kinds of callable. All become nodes, but their origin and the way they are resolved differ:

| Source | In code | Node | Resolution |
|---|---|---|---|
| **Tool / MCP** | `await tools.github.getFiles({ pr })` | `tool` node | symbol belonging to the `Tools` interface (generated by the registry) |
| **Library function** — a function the user writes and **stores independently**, with an input/output schema, reused across flows | `import { filterAuthChanges } from "@flows/lib"` then `filterAuthChanges(files)` | `function` node (label/icon/schema from the registry) | symbol of the import from the function library |
| **Local function** — a named function in the flow file itself | `function normalize(x) {...}` then `normalize(data)` | `function` node (schema inferred from the TS signature) or a minimal node | local symbol |
| **Inline code** — a statement/expression that is none of the above | `const r = x.reduce(...)` | `code` node, source kept verbatim | fallback |

A library function is first-class, on a par with a tool: the user can write a new function (in the UI via Monaco, or AI-generated), declare its input/output and **save it to the function library** — from then on it appears in the node palette like any tool and can be reused in any flow. See [05-registry.md](05-registry.md) §4.

## 2. Supported semantics (MVP)

Inside the body of the `flow` function, the analyzer understands:

| Construct | Node |
|---|---|
| `await tools.<ns>.<fn>(args)` | Tool node |
| calling a library function (imported from the function library) | Function node |
| calling a local named function | Function node / code node |
| `const x = await ...` | Data output (port) of the node |
| `if / else` | Condition node + 2 control branches |
| `for...of` | Loop node (body is a subgraph) |
| `while (cond)` | Loop node (kind: `while`, condition editable) + bound-check diagnostic |
| `try / catch (/ finally)` | Try node — body/catch(/finally) are subgraphs, `error` edge |
| early `return` | Output node ("End Flow") |
| `break` / `continue` inside a loop | Jump node inside the loop subgraph |
| `Promise.all([...])` | Parallel node + merge |
| Template literal in an argument | Expression displayed as `{{ }}` |
| `for await...of` | Same as `for...of` |
| Everything else | Custom code node (kept verbatim). Including: classic `for(;;)`, `do...while`, optional chaining on tools (`tools.github?.getFiles?.()`), and `await`/tool calls hidden inside an expression ([04-analyzer.md](04-analyzer.md) §1.4 — always with a diagnostic, never silently) |

This list is extended only deliberately (see [09-future.md](09-future.md)); every construct added multiplies the complexity of the analyzer plus the patcher rather than adding to it.

## 3. AI style guide

A standard system prompt (shipped with the library; `codeflow generate` writes it into a workspace as `prompts/flow-style.md`, and the canonical text lives in core as `FLOW_STYLE_PROMPT`) tells the AI how to generate CodeFlow-friendly code:

- Every step of the flow is one `await` call **standing as its own statement** (`const x = await tools...`), at the top level of the flow body or directly inside an `if`/`for`/`while`/`try` block — **never** put a tool call inside an expression: not in a condition (`if (await tools.x.y())` ❌ — hoist it into `const ok = await tools.x.y()` first), not as an argument to another call, not inside a callback (`Promise.all(prs.map(...))` ❌ — use `for...of`, or `Promise.all([...])` with an array literal).
- For parallel steps, write the calls **inside the array literal**; do not hoist them into `const aPromise = tools.x.one({…})` first — an un-awaited call sitting in a `const` is not recognised as a step and the parallel branch disappears from the graph.
- Assign results to a `const` with a meaningful name — the variable name becomes the label of the data edge in the UI. Never assign a call straight into an outer `let` (`issue = await tools.jira.getIssue(…)` ❌): take the result in a `const` first, then copy it.
- Complex conditions → extract into a named function with a descriptive name (`isAuthChange`) — that becomes a readable node instead of a long expression.
- Complex data transformations → extract into a named function — that becomes one compact custom code node instead of statements scattered across the body.
- `try/catch` wraps **the group of steps that can actually fail** (one tool call, or a few adjacent ones), never the whole flow body — the narrower the catch, the more readable the graph.
- `while` must have a **stopping condition visible in the code** (a counter/attempt limit updated in the body) — the analyzer warns when it cannot recognise a bound.
- `return`/`break`/`continue` are the normal way to write guards and early exits; do not use recursion in the flow body — if you need it, wrap it in a named function.
- **Imports**: `import type { Tools } from "../generated/tools"` is type-only — never import a *value* from `generated/`. Value imports come from `@flows/lib`; type-only imports may come from anywhere. Any other value import degrades the statements that use it to opaque code nodes.
- **A call in a plain statement is a hidden step too** — the mistake long flows make most often. Plain data in a statement is fine (`failed += 1;`, `const found: Item[] = [];`); a **call** is not: `failures.push({ path, reason })`, `const stamp = new Date().toISOString()`, `passed = matches(text)` all disappear into code nodes. Declare a named function in the same file and give each its own statement (`recordFailure(failures, path, reason);`) so it becomes a function node. Collecting, deriving and testing a value are steps; make them look like steps.

The style guide is guidance for the AI, not a validator that rejects code. Code that ignores it → more custom code nodes, fewer meaningful ones — still correct, just less legible.

## 4. MVP scope

- **A flow is 1 file** + **imports from the function library**. Library functions are resolved through registry metadata (schema, label) — the analyzer does **not** analyze across files into a library function's body (that body only opens when the user clicks "Edit Code"). Imports from anywhere else → opaque code node.
- **TypeScript only**: JavaScript is out of the MVP (the AI generates TS; missing types make tool resolution less reliable). It can come back later if needed.
- **One flow per file**: with multiple exports, only the default export is analyzed; the rest produce warning diagnostics.
